# Porting Enableton's tool catalogue into AbletonMCP

Enableton (EnAbleton, `v0.1.0-beta.2`) publishes a machine-readable catalogue of
its tools at `docs/tool-catalog.json` in its repository: **242 tools**
(156 from `mcp-server-ableton-live==1.8.1` plus 86 Enableton additions). This page
records exactly which of those can live in this repo, what has been ported, and
why the rest need work in Live rather than in Python.

## The numbers

Measured against this repo at `2.0.0` (128 MCP tools, 245 REST-whitelisted
commands, 257 commands handled by `AbletonMCP_Remote_Script/__init__.py`):

| Bucket | Count | Meaning |
|--------|-------|---------|
| Catalogue tools | 242 | Enableton's full typed surface |
| Already exposed here | 50 | Same tool name; ignored per the "skip duplicates" rule |
| Enableton-only | 192 | The real porting surface |
| **Ported in this repo** | **30** | `MCP_Server/enableton_tools.py` — 18 direct plus 12 adapted onto existing commands |
| Remaining | 162 | 116 portable with today's bridge (44 need no bridge call at all); 46 still need new commands |
| Blocked on new bridge commands | 46 | Need 42 commands this Remote Script does not implement |

Of the 170 tool functions in the upstream wheel, 68 are fully backed by commands
this Remote Script already implements, 44 need no bridge call at all (pure Python:
offline `.als` analysis, generators, recipes), and 58 need commands we lack. The
53 distinct missing commands are the real cost of the remaining port.

`docs/enableton-port-report.json` is generated by
`scripts/classify_enableton_tools.py` and carries the per-tool detail.

## What was ported (30 tools)

Every ported tool carries an MCP behaviour hint (`readOnlyHint`, `destructiveHint`,
`idempotentHint`) so clients can tell reads from writes and flag destructive calls.

All 158 tools in the server carry hints, including the 128 pre-existing ones
(annotated by `scripts/apply_tool_hints.py`).

The first group calls commands the bundled Remote Script already handles, so they
run against an unmodified server:

| Area | Tools |
|------|-------|
| Transport | `continue_playing`, `stop_all_clips`, `tap_tempo`, `set_arrangement_time` |
| Global settings | `set_swing_amount`, `set_groove_amount`, `set_crossfader`, `set_clip_trigger_quantization`, `set_session_automation_record`, `set_arrangement_overdub`, `re_enable_automation` |
| Return tracks | `create_return_track`, `delete_return_track` |
| Clips and MIDI | `get_clip_info`, `quantize_clip`, `humanize_clip`, `detect_clip_key`, `detect_track_key` |

Differences from Enableton's originals, stated plainly:

* `quantize_clip` accepts Enableton's grid names and converts them to the beat
  value this bridge expects; `amount` is passed through.
* `humanize_clip` is implemented here from `get_clip_notes`/`set_clip_notes` with a
  seeded RNG; Enableton's exact jitter distribution is not reproduced.
* `detect_clip_key` / `detect_track_key` use Krumhansl-Kessler profiles with
  `kk` (note count) or `duration` weighting; Enableton's `weight` semantics may
  differ in detail.
* `set_clip_trigger_quantization` takes the bridge's integer scale (0 None → 4 bar)
  rather than Enableton's `value`.

### Adapted onto existing commands (12 tools)

These tool names existed upstream but this Remote Script exposes the same
capability under a different command name, so the tool adapts rather than the
bridge being changed:

| Enableton tool | Bridge command used | Fidelity note |
|----------------|--------------------|---------------|
| `back_to_arranger` | `trigger_back_to_arrangement` | Exact |
| `get_grooves` | `get_groove_pool` | Exact |
| `get_track_meters` | `get_track_output_meter` | L/R output meter only |
| `get_drum_pads` | `get_drum_rack_pads` | Exact |
| `get_group_info` | `get_track_is_grouped` | Grouped flag only, no member list |
| `get_track_routing` | `get_track_input_routing` + `get_track_output_routing` | Two reads, merged |
| `clear_automation` | `clear_clip_automation` | Param matched by name, `device_index` unused |

## What is blocked, and why

The 42 bridge commands named in `docs/enableton-port-report.json` under `missing_commands` now have handlers in `AbletonMCP_Remote_Script/enableton_commands.py`. The MCP server wraps them in `MCP_Server/gap_commands.py` (`get_session_snapshot` stays in `enableton_tools.py` and calls the new command). The REST whitelist includes the same names, so `POST /api/command` can send them. They still have to be verified with Live open. Restart Live after copying the remote script, or the new names answer "Unknown command".

174 tools need live-side work beyond a command name. Grouped by the commands that were missing when the report was generated:

| Domain | Missing commands | Example tools |
|--------|------------------|---------------|
| Arrangement clips | `get_arrangement_clips`, `delete_arrangement_clip`, `duplicate_clip_to`, `duplicate_session_clip_to_arrangement`, `create_take_lane`, `back_to_arranger` | `duplicate_to_arrangement`, `list_arrangement_clips` |
| Devices on returns/master | `load_device_to_return`, `load_device_to_master`, `get_return_device_parameters`, `get_master_device_parameters`, `rack_variation` | nested-device tools |
| Racks and routing | `get_device_routing`, `get_track_routing`, `get_group_info`, `get_drum_pads` | drum-rack and routing tools |
| Mixing meters | `get_track_meters`, `get_master_meters` | `get_track_meters`, mix analysis |
| Grooves | `get_grooves` | groove pool tools |
| Session/scale reads | `get_session_snapshot`, `get_scale_info`, `get_grooves` | `session_snapshot`, `analyze_mix` |
| Note editing | `edit_notes`, `clip_op` | partial note tools |
| Batched writes | `batch` | Enableton's guarded batches |
| Navigation | `jump_to_cue`, `jump_to_locator`, `jump_by` | navigation tools |
| Misc | `preview_browser_item`, `create_audio_clip`, `clear_automation`, `capture_and_insert_scene` | browser preview, audio import |

Run `scripts/classify_enableton_tools.py` with the catalogue and the upstream
map to regenerate this split after any change.

## Three ways to close the gap

1. **Pure-Python port (lowest risk, no Live needed).** Port the 44 upstream tools
   that make no bridge call — offline `.als`/`.adg` analysis, music generators,
   recipes, `analyze_mix`, `session_diff`, `describe_capabilities`. They only need
   the MIT-licensed upstream modules and their data files vendored in.
2. **Implement the 53 missing commands in this Remote Script (medium risk).**
   Do it domain by domain, starting with arrangement clips and routing since they
   unblock the most tools. Every command has to be written against Live's LOM and
   verified with Live open.
3. **Adopt upstream's Remote Script wholesale (highest risk).** `mcp-server-ableton-live`
   derives from the same original remote script and speaks the same JSON protocol on
   port 9877, so swapping it in would unlock its whole tool set at once — but it is
   not a superset of this repo's 257 commands, so the M4L device and the REST
   endpoints would need re-verification, and it can only be validated with Live running.

Recommended order: 1, then 2 domain by domain, and only consider 3 if this repo is
meant to become a thin shell over upstream rather than its own implementation.

## Verification status

The ported module is checked for import, registration, hint coverage and schema
validity without Live, and the composed tools (`edit_notes`, `get_track_routing`,
`jump_to_cue`, `detect_track_key`) are exercised against a fake bridge. None of the
30 tools has been run against a live Ableton set; `detect_*`, `humanize_clip`,
`quantize_clip` and `edit_notes` in particular need a real MIDI clip to confirm
their results.
